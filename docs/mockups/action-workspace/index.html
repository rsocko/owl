    Migration plan & decisions

    What moves, changes, stays separate, or remains open.

    Promote into the shared workspace

    • Stable tabs, contextual default. Document tabs retain the shared Metadata, Actions/Decision, Related, OCR order. Action Review opens Actions; Needs Review opens Decision.
    • Actions stay editable with explicit Save. The selected action uses the same type-aware editable fields as Inbox instead of requiring a separate Edit mode. Lifecycle outcomes wait until field edits are saved so the audit event is intentional.
    • Documents appear once; actions stay distinct. The rail contains one row per document. Its Actions tab shows the complete set of inferred and manually created actions, with an independent lifecycle for each action.
    • Action outcomes are visibly scoped. Multi-action documents offer Done beside each action and label the sticky outcome bar as applying only to the selected action.
    • Add and history stay inline. New actions are created beside the document’s action set, and each selected action exposes its own audit history in the same tab.
    • Document-derived work controls. Pay, call, email, sign, and source links appear beside the action they support.
    • Complete lifecycle. Done, remind later, won't do, not an action, reopen, and audit history stay available.
    • Correction without context switching. Type-aware fields, confidence reasoning, urgency, amount, reference, and due date remain editable.
    • Related evidence. Receipts, revisions, reminders, and authoritative documents remain one tab away.

    Adapt for the left rail

    • Show each document once with its thumbnail, correspondent, document type, action count and types, nearest deadline, and combined amount—not duplicate rows for each action.
    • Provide search, lifecycle status, due-window and action-type facets, sorting, and a manual desktop rail-collapse control.
    • Preserve keyboard next/previous navigation and selection through filtering.
    • Group only when it improves scanning; overdue and today can become section headers without rebuilding the old dashboard.

    Defer as a possible later table view

    • Wide many-column comparison and bulk outcomes across unrelated documents are not required for the initial migration.
    • If usage proves a need, add a contextual table or Manage view inside Actions and Needs Review—not a new top-level destination.
    • Pipeline run controls and system status, which are administration—not review.
    • Needs Review confidence thresholds or bulk decisions require separate safety validation before implementation.

    Removed from the primary review UI by choice

    • The Action Queue detail drawer is replaced by the persistent workspace; keeping both would create two competing detail experiences.
    • Grouped-list versus table toggle leaves the initial review surface. A contextual table view is tracked as a later enhancement if wide comparison or bulk work proves necessary.
    • Pipeline status and run controls move to Operations. They describe system execution, not the decision on the current document.
    • Acknowledged is removed from the target experience. It was a legacy “seen” state created by a control that no longer exists—not a completed or resolved outcome. Action Review uses explicit Pending, Done, Remind later, Won’t do, and Not an action outcomes instead.
    • FILE actions are omitted entirely from the target Action Review UI. Filing is an Intake operation, and the separate legacy-data cleanup should not shape the future workspace.
    • Global bulk controls inside the document workspace are removed to prevent an outcome intended for one evidence set from affecting unrelated items.

    Material behavior changes

    • Accept in Needs Review does not mean Done. It establishes trust and may publish a new pending action.
    • Confidence becomes explanatory. The UI pairs the score with the reason, conflicting fields, and alternative evidence instead of showing a bar alone.
    • Different queues show different facts. Action Review emphasizes due date, amount, urgency, and work links; Needs Review emphasizes review type, reason, confidence, age, and priority.
    • Multi-document reviews adapt the center pane. A relationship item shows side-by-side evidence instead of forcing every review into a single-document preview.
    • Action classification reviews are document reviews. Needs Review shows every proposed action attached to the document and accepts or corrects the set together.
    • Resolved decisions remain revisable. Revising a decision appends audit history; if downstream work is already completed, OWL warns and preserves that completed history rather than rewriting it.
    • Queue advancement respects context. Save-and-next and resolution outcomes select the next item in the active lifecycle, facet, search, and sort view.
    • Not an action is separated from rejection. For action classification it records a false positive; for a proposed relationship, Reject means the pairing is wrong.

    Possibly missed or intentionally not fully mocked

    • Statement split/merge, duplicate consolidation, grouping correction, and orphan search still need production API contracts and complete edge states.
    • Source conflicts, permission failures, loading, empty, and stale-analysis states need production designs.
    • Bulk selection, shift-select, keyboard Y/N shortcuts, and confidence-threshold confirmation are deferred with the possible table view.
    • Multiple actions use one document rail row plus an in-tab action set; production must validate ordering, bulk outcomes, and dirty-state behavior.
    • Real Paperless thumbnails, dark theme verification, localization, and narrow-screen focus management remain implementation requirements.

    Important semantic boundary

    Done means the real-world action was completed. Won't do means it was real but intentionally declined. Not an action means OWL was wrong and should retain classifier feedback. Next doc changes only the selected document. None of these implicitly files or edits the Paperless document.

    Mark as not an action?

    Use this only when OWL identified work that does not exist. The correction is retained as classifier feedback; it does not file or edit the Paperless document.
